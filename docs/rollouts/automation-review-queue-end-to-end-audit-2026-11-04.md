## Executive verdict

**B. SYSTEM_WORKS_BUT_HAS_BOUNDED_DEFECTS.**

The owner decision and second confirmation are not decorative. In the audited eBay history, 159 owner approvals were found. Of these, 145 received a second execution request: 56 reached `EXECUTED` with complete postflight and idempotency evidence, 88 expired safely during revalidation with zero business writes, and one failed before a business write. Fourteen approvals never received an execution request. All 48 executed price plans have matching retained `price_history` evidence; all eight executed stock plans have the intended postflight stock delta.

Most apparent repetition is expected offer-level lifecycle: a publisher supersession, a new capture, a changed commercial fact, or a successful execution followed by a later change. A product title is not the queue identity. The effective identity is the retailer/offer and bound variant, plus the source and plan fingerprints.

There is, however, one confirmed contract defect. The eBay reconciliation producer emits `HARD_PRICE_ANOMALY`, and the protected eBay worker understands it, while the JavaScript publisher allowlist, publication RPC allowlist, and adapter registry reject or omit it. On production run `41836635201` this stopped the entire 85-row reconciliation batch before publication. It can delay supersession/resolution and leave old database rows visible until a later successful publication, but it does not reverse a successful catalogue write and it does not explain the 27 historically verified cases where a successfully executed offer later changed again.

## 2. Architecture and lifecycle

### 2.1 Boundaries

The current implementation separates six concerns:

1. **Source refresh** captures retailer evidence and produces a dry-run/reconciliation manifest. It does not itself represent owner approval.
2. **Publication lifecycle** validates that manifest and calls `publish_automation_review_queue_changes(jsonb)`. The RPC creates/refreshes/supersedes/resolves review rows and verifies that catalogue counts/hash did not change.
3. **Owner decision** in `app/admin/automation-review/decision/route.ts` changes only a valid `PENDING` review row to `APPROVED`, `REJECTED`, or `IGNORED` and records the authenticated actor. It checks fingerprints, expiry, compatibility, and the impact acknowledgement. First approval alone does not change offers, mappings, products, variants, or price history.
4. **Second confirmation / execution request** in `app/admin/automation-review/execute/route.ts` rechecks status, source and plan fingerprints, decision evidence, expiry, and adapter resolution, then queues through `queue_automation_review_execution`. It may dispatch the guarded workflow when configured; otherwise the scheduler is the fallback. It does not directly mutate catalogue data.
5. **Worker execution** in `scripts/automation-review-queue-worker.js` claims the request, moves through revalidation/checkpoints, invokes the resolved protected retailer adapter, and records execution evidence.
6. **Catalogue write** occurs only inside the protected retailer apply path after source, plan, database-before-state, fingerprint, and policy revalidation. Postflight and idempotency checks are required before a successful terminal state.

`app/admin/lib/automationReviewQueueData.ts` joins the latest execution request to each review. The UI can therefore show `QUEUED` or `DISPATCHED` while the review row itself is still `APPROVED`. At the worker checkpoint the review becomes `EXECUTING`, then reaches `EXECUTED`, `FAILED`, or `EXPIRED`.

`scripts/lib/automation-review-execution-coordinator.js` is referenced by tests but is not the production queue-worker runtime. Its narrower legacy operation map is not evidence of a live divergence.

### 2.2 State meanings

| State | Stored on | Meaning |
|---|---|---|
| `PENDING` | review | Fresh owner/technical decision candidate. |
| `APPROVED` | review | Owner approved; no catalogue write is implied. |
| `QUEUED` | execution request | Second confirmation created a request. |
| `DISPATCHED` | execution request | Workflow dispatch was recorded; scheduler fallback may otherwise claim it. |
| `EXECUTING` | review/request | Worker claimed and began protected revalidation/execution. |
| `EXECUTED` | review/request | Protected apply and required postflight completed. |
| `FAILED` | review/request | Execution failed; evidence determines whether writes were zero or uncertain. |
| `EXPIRED` | review/request | Evidence or database state was no longer safe to apply. |
| `REJECTED` | review | Owner rejected; no execution. |
| `IGNORED` | review | Owner dismissed; no execution. |

`QUEUED` and `DISPATCHED` are execution-request states, not allowed review-row statuses. This is why the UI summary must be reproduced with joined request state rather than raw review status alone.

Thirty-six of the 56 current offer states still equal the last audited intended state. Twenty changed later. A later state does not invalidate the retained postflight evidence; it is precisely the condition that can create a later, legitimate review.

Approval and publication do not change comparison depth. Only a successful protected apply can do so. Price-only execution changes price but not retailer count. The retained schema does not preserve a full historical per-product/per-retailer freshness and stock snapshot at each execution timestamp, so exact 2+ and 3+ comparison-depth gains for the two restorations cannot be reconstructed honestly. Historically provable gains are therefore zero; two restorations have unknown depth impact. No-depth-change is directly established for the 48 price-only changes; the six removals reduced or left unchanged effective depth rather than increasing it.

## 9. Confirmed eBay publisher contract defect

Production workflow run `41836635201` at head `1d30a68…` completed the core eBay refresh and its apply, postflight, and idempotency stages. The later `refresh-review-queue` job failed while building fresh Review Queue changes with `Error: Unknown reason code in row 2`; the publish step was skipped, so the publication RPC was never called.

The retained source artifact `ebay-offer-refresh-41836635201-1` (artifact ID `13328715529`) contains 85 proposed review rows. Zero-based row 2 is offer `2544`, `UPDATE_PRICE`, reason `HARD_PRICE_ANOMALY`: price before `84.81`, proposed `108.77`, absolute delta `23.96`, above the configured hard threshold of `20`.

The mismatch is exact:

| Layer | Evidence | `HARD_PRICE_ANOMALY` |
|---|---|---:|
| Producer | `scripts/automation-review-reconciliation-dry-run.js:214` | Emits it for a hard price review. |
| Protected worker | `scripts/automation-review-ebay-worker.js:79` | Explicitly recognizes and revalidates it. |
| JavaScript publisher | `scripts/lib/automation-review-publisher.js:19-35,113` | Missing from `REASON_CODES`; throws the observed row error. |
| SQL publication RPC | `supabase/migrations/20260831110000_create_automation_review_queue_publication_rpc.sql:262-271` | Missing from allowed reasons; would reject the request. |
| Adapter registry | `config/automation-review-execution-adapters.json:11` | eBay `UPDATE_PRICE` omits the reason, so execution resolution would reject such a row. |
| UI capability matrix | operation-level | Calls eBay `UPDATE_PRICE` review-executable; it does not expose the reason-level mismatch. |

No shared canonical reason-code registry prevents these copies from drifting. This is a **CONFIRMED CONTRACT DEFECT**.

Because JavaScript validation fails before the RPC, one hard-anomaly row aborts the entire batch. That prevents creation of the new anomaly row and prevents refresh, supersession, and resolution of every other row in the same manifest. The last successful eBay publication was 2026-11-03T13:18:53Z; there are 42 eBay publications among 195 total publications. Current stored eBay statuses are 77 `PENDING`, four `APPROVED`, 35 `EXPIRED`, and 29 `EXECUTED`. Eighty-one stored `PENDING`/`APPROVED` rows are clock-expired, so current UI lifecycle logic puts all 145 eBay rows in `COMPLETED`, producing eBay `DECIDE = 0`.

The failed batch can leave old rows active in storage and delay lifecycle reconciliation until a later successful publication. It can therefore contribute to owner-visible stale/reappearing presentation. It cannot undo prior catalogue writes, and the audited historical transition set contains zero proven `PUBLISHER_RESOLVE_FAILED`, `DUPLICATE_ACTIVE_REVIEW_BUG`, or `STALE_REVIEW_NOT_CLOSED` transitions. The defect is not the cause of the 27 proven successful-then-changed-again recurrences.

## 14. User-facing simplification recommendation

The five summary buckets should answer exactly one question each:

- **Do Twojej decyzji:** a currently valid row where the owner can approve, reject, or ignore.
- **Zatwierdzone do wykonania:** approved and safe, but still waiting for the second confirmation.
- **System wykonuje:** request queued, dispatched, or executing; show the last checkpoint and run link.
- **Zostaw technikowi:** cannot be resolved from this panel; show the exact reason such as identity-only, unsupported operation, missing adapter, or source failure.
- **Zakończone:** executed, rejected, ignored, expired, safely failed, or otherwise terminal; display the terminal reason, not just the bucket.

Each card should visibly show Product, Variant, Retailer, Offer ID, operation/reason, source capture time, expiry, and one of: `Previously reviewed`, `New evidence since last review`, `Execution succeeded`, `Execution expired safely`, or `Same product, different variant/offer`. Product grouping may aid scanning, but the offer/variant row must remain the actionable identity.
